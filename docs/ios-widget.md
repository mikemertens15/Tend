# The iOS widget

The groundwork is done and lives in this repo and in the database. The Swift is
not written, because it can't be built from Windows. This file is the handover:
everything the widget needs already exists and is verified, so the Mac session is
a UI job rather than a design job.

## What already exists

- **`public.widget_agenda(p_token text, p_days int)`** — one `SECURITY DEFINER`
  Postgres function that returns the whole widget payload as JSON. No session, no
  table access, one round trip.
- **`public.widget_tokens`** — per-member tokens, generated by a database default,
  revocable, with `last_used_at` stamped on every read.
- **Token management UI** — Calendar → **📱 Widget**. Create one per device, copy
  the link, revoke it if a phone goes missing.
- **A reference rendering** — `#/widget/<token>` renders the payload in roughly
  the proportions of a large iOS widget. Open it in a browser to see exactly what
  the endpoint returns, and to have something to compare the SwiftUI version
  against.

## The security shape

Worth stating plainly, because this is the app's second public surface.

- A widget token belongs to **one member**, not the household. The agenda is
  built through that member's eyes, so it includes events marked private to them
  — a widget that hid your own calendar from you would be pointless.
- Only that member can list, create or revoke their own tokens. The RLS policy on
  `widget_tokens` is keyed on `private.current_member_id(household_id)`, so
  another member in the same house gets an empty list rather than a URL that
  reads your private calendar.
- The underlying tables gain **no anon policies**. Everything a token holder can
  reach goes through `widget_agenda`, which validates the token and then returns
  exactly one whitelisted shape.
- It is **read-only**. There is no write path, unlike the sitter link.
- A leaked token is worth one person's next fortnight of appointments, until it
  is revoked.

## The endpoint

It's a normal Supabase RPC, so it's a `POST` with the publishable key:

```bash
curl -s -X POST "$VITE_SUPABASE_URL/rest/v1/rpc/widget_agenda" \
  -H "apikey: $VITE_SUPABASE_ANON_KEY" \
  -H "Authorization: Bearer $VITE_SUPABASE_ANON_KEY" \
  -H "Content-Type: application/json" \
  -d '{"p_token":"<token>","p_days":3}'
```

`p_days` counts today as the first day and is clamped to 1–14 server-side. A
small widget wants 1, a medium 2–3, a large 4–5.

A revoked, expired or nonsense token returns `null` — deliberately
indistinguishable, so a token can't be probed for existence.

## The payload

```jsonc
{
  "household": "My House",
  "member": "Mike",
  "today": "2026-08-18",
  "generatedAt": "2026-08-18T22:27:42Z",
  "openChores": 3,

  // null when there's no shift today. This is the one bit of live state a
  // widget can usefully show that isn't an appointment.
  "work": {
    "title": "Shift",
    "job": "Wegmans",
    "scheduledStart": "06:00:00",
    "scheduledEnd": "15:00:00",
    "actualStart": "06:07:00",
    "actualEnd": null,
    "breakMinutes": 0,
    "onBreak": true,
    "clockedIn": true,
    "status": "worked"
  },

  "days": [
    {
      "date": "2026-08-18",
      "events": [
        {
          "title": "Organic Chem",
          "kind": "school",          // event | birthday | appointment | school | trip | holiday | work
          "startTime": "09:30:00",   // null when all-day
          "endTime": "10:45:00",
          "allDay": false,
          "continuation": false,     // a later day of a multi-day event
          "location": "Baker Hall 201",
          "note": null,
          "color": "#2f8079",        // the calendar's colour, a real hex
          "icon": "🎓",
          "calendar": "School",
          "who": "Mike"              // null when it's the household's
        }
      ]
    }
  ]
}
```

Times are wall-clock `time` values with no zone, matching how the rest of Tend
stores them. Sort within a day by `allDay` first, then `startTime` — the server
already returns them in that order.

## What to build on the Mac

1. **A SwiftUI app target** that wraps the existing web app (or just holds the
   settings screen — the widget is the point, the app doesn't have to do much).
2. **A widget extension** with `systemSmall`, `systemMedium` and `systemLarge`
   families, plus an accessory family for the lock screen if it's worth it.
3. **Shared storage for the token.** Put the app and the extension in the same
   **App Group** and keep the token in the shared container (or Keychain with an
   access group). The extension can't read the app's `UserDefaults` otherwise.
4. **A `TimelineProvider`** that fetches the payload and returns entries. The
   sensible policy is one entry per event boundary in the returned window, with
   `.after(nextRefresh)` set to about 30 minutes — iOS budgets roughly 40–70
   refreshes a day, so a fixed 15-minute poll will be throttled and a
   boundary-driven timeline will not.
5. **Deep links back into the app** via a custom URL scheme, so tapping an event
   opens the calendar on that day.

### Sketch

```swift
struct AgendaEntry: TimelineEntry {
    let date: Date
    let payload: WidgetAgenda
}

func fetchAgenda(token: String, days: Int) async throws -> WidgetAgenda {
    var request = URLRequest(url: URL(string: "\(supabaseURL)/rest/v1/rpc/widget_agenda")!)
    request.httpMethod = "POST"
    request.setValue(anonKey, forHTTPHeaderField: "apikey")
    request.setValue("Bearer \(anonKey)", forHTTPHeaderField: "Authorization")
    request.setValue("application/json", forHTTPHeaderField: "Content-Type")
    request.httpBody = try JSONEncoder().encode(["p_token": token, "p_days": "\(days)"])

    let (data, _) = try await URLSession.shared.data(for: request)
    return try JSONDecoder().decode(WidgetAgenda.self, from: data)
}
```

The publishable (`anon`) key is safe to ship in the binary — it is safe in the
browser for the same reason, and every table it can reach is behind RLS. The
**token** is the secret, and it belongs in the App Group container rather than
in source.

## If it should ever write

It doesn't today, and that's deliberate. But "clock in from the widget" is the
obvious next ask, and the shape is already there: add a second `SECURITY DEFINER`
function alongside `widget_agenda` that takes the same token, confines its write
to one row shape in `work_shifts` for that member's own shift today, and expose
it as an `AppIntent` so the button works without launching the app. That is the
same pattern `sitter_toggle_meal` already uses.
